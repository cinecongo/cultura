# ADR-002 — Internationalisation : catalogues typés maison (PT-AO / FR / EN)

- **Statut :** Proposé — validation humaine requise (Gate G0)
- **Date :** 2026-11-23
- **Décideurs :** architecte + porteur de projet
- **Concerne :** P0.4, P1.4, P8.4
- **Documents liés :** cahier §1.1, §6, §9.1, A1, A6 ; guide §8.2, §9 P1.4

## Contexte

- Trois langues dès la V1 : portugais d'Angola (principal), français, anglais.
- L'interface est traduite ; **le contenu reste dans sa langue d'origine** (pas de traduction automatique).
- URLs localisées (`/pt/...`), `hreflang`, `<html lang>` correct.
- Contrainte forte : le build mobile est un export statique. Un middleware Next.js ne s'exécute pas dans l'APK.
- Budget : JS initial ≤ 150 Ko gzip. « Pas de bibliothèque lourde pour un besoin trivial » (guide §8.3).
- Le guide exige un test qui échoue si une clé manque dans une langue.

## Options étudiées

| Option | Avantages | Inconvénients |
|---|---|---|
| **A. Catalogues typés maison + `Intl`** | Zéro dépendance, identique serveur/client/export, typage strict des clés, ~2 Ko, contrôle total du formatage | Pas d'ICU avancé (sélection de pluriel riche, genres), outillage à écrire (test de parité) |
| **B. `next-intl`** | DX excellente, ICU, routing intégré, communauté active | Provider serveur/client à scinder pour l'export, middleware inutilisable en mobile, dépendance et surface d'API supplémentaires |
| **C. `react-i18next`** | Très répandu, interpolation et pluriels | Orienté client, initialisation globale, poids et complexité pour un besoin simple |
| **D. Lingui (compilation)** | Messages compilés, très léger à l'exécution | Étape de build supplémentaire, format de messages à apprendre, friction avec l'export |

## Décision

**Option A**, avec une interface suffisamment étroite pour migrer vers `next-intl` plus tard sans réécrire les écrans.

### 1. Structure

```
src/lib/i18n/
├─ index.ts          // getLocale, t, tp, formatters
├─ messages/
│  ├─ pt.ts          // source de vérité du type Messages
│  ├─ fr.ts          // satisfait Messages
│  └─ en.ts          // satisfait Messages
└─ format.ts         // Intl : dates, heures, nombres, Kz
```

- `pt.ts` définit le type ; `fr.ts` et `en.ts` sont annotés `satisfies Messages`. Une clé manquante **casse le typecheck** (preuve P1.4).
- Clés en anglais, plates ou imbriquées d'un seul niveau, jamais construites dynamiquement.
- Aucune chaîne d'interface en dur dans un composant. Un test grep échoue si du texte visible est écrit directement dans le JSX.

### 2. API

```ts
t(locale, 'today.title')
t(locale, 'event.count', { count: 8 })
tp(locale, 'event.count', 8)          // pluriel via Intl.PluralRules
formatDate(locale, date)              // « 24 de novembro de 2026 »
formatTime(locale, date)              // « 18h00 » (PT), « 18 h 00 » (FR), « 18:00 » (EN)
formatKz(locale, 1500)                // « 1 500 Kz »
```

- Interpolation par `{nom}` uniquement. Pas d'expressions dans les messages.
- Les pluriels utilisent `Intl.PluralRules(locale)` : catégories `one`, `other` (et `many` si nécessaire).
- Les montants sont des entiers de kwanzas ; jamais de flottant pour la monnaie.

### 3. Résolution de la langue

Ordre : segment d'URL `/pt|/fr|/en` → cookie `cultura_locale` → `Accept-Language` → `pt`.
Un sélecteur de langue est toujours accessible (en-tête web, écran compte sur mobile). Le choix est mémorisé.

### 4. Formats

| Élément | PT-AO | FR | EN |
|---|---|---|---|
| Date longue | 24 de novembro de 2026 | 24 novembre 2026 | 24 November 2026 |
| Heure | 18h00 | 18 h 00 | 18:00 (24 h) |
| Nombre | 1 500 | 1 500 | 1,500 |
| Monnaie | 1 500 Kz | 1 500 Kz | 1,500 Kz |

- **Fuseau :** stockage UTC, affichage `Africa/Luanda` (UTC+1, sans heure d'été). Jamais l'heure du serveur.
- `pt-AO` n'est pas garanti complet dans tous les moteurs `Intl` : prévoir un repli documenté sur `pt` pour le formatage, sans changer le texte.
- `en-GB` (24 h) plutôt que `en-US`.

### 5. SEO

- Préfixe de locale obligatoire, y compris pour la langue par défaut.
- `<html lang="pt-AO">`, `<link rel="alternate" hreflang="pt|fr|en|x-default">`.
- Sitemap par langue ; canonical auto-référent.

### 6. Gouvernance des textes

- Vocabulaire imposé : `i18n/GLOSSAIRE.md`.
- Termes interdits scannés automatiquement : `publicação`, `publication`, `post`, `compte artiste`, `plataforma` (en copy publique).
- Toute nouvelle clé est ajoutée **dans les trois langues dans le même commit**.
- Les traductions PT sont relues par un locuteur angolais avant lancement (P8.4) ; les choix de vocabulaire (ex. « agente cultural » vs « ator cultural ») y sont validés.

## Conséquences

**Positives**

- Comportement identique sur le web SSR et dans l'APK.
- Typecheck = test de complétude des clés.
- Aucune dépendance à maintenir pour une fonctionnalité stable.

**Négatives / coûts**

- Pas d'ICU avancé : les messages à pluriel complexe devront être écrits autrement (phrases séparées).
- Le test de parité et le scanner de texte en dur doivent être écrits (P1.4).
- Migration ultérieure vers `next-intl` à prévoir si les besoins éditoriaux augmentent : l'interface `t()` isole le changement.

## Vérification (P1.4)

1. `npm run typecheck` échoue si une clé est retirée de `fr.ts` (test de régression documenté).
2. Test unitaire : `t()` retourne la chaîne attendue dans les 3 langues ; `tp()` gère 1 et 8.
3. Test : changement de langue → URL, cookie et `<html lang>` cohérents.
4. Test : aucun texte visible hors clé i18n dans les composants.
5. Preuve de formatage : date, heure et Kz corrects dans les 3 langues à `Africa/Luanda`.
